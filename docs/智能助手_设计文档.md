## 0. 设计约束与质量门禁

### 0.1 三条硬约束

1. **单一执行路径**：所有动作最终调用既有业务服务的唯一入口（`WarningService`、`WorkflowService`、`RuleService`、`DeliveryDispatcher`、`ReportIntake`）。助手层只做解析、授权、预览、编排、审计，**不复制任何业务逻辑**。
2. **零死代码**：注册表只登记已实现的动作；每个导出必须有调用方；每个字段必须被读；退役接口在同一期内删除，不留"以后可能用"的别名。§10 给出逐条清单。
3. **可回滚**：每期改动都有 feature flag 或独立表；迁移只加不删，回滚点明确。

### 0.2 设计原则

| # | 原则 | 落地方式 |
| --- | --- | --- |
| 1 | 依赖单向 | `api → service → action → domain/infra`；动作层不得 import API 层 |
| 2 | 一个真源 | 动作目录只在注册表；会话状态只在会话存储；执行状态只在 `control_actions` 表 |
| 3 | 类型闭合 | 动作参数一律 Pydantic 模型，`extra="forbid"`；禁止 `dict[str, Any]` 透传到业务层 |
| 4 | 失败显式 | 每个失败有错误码；不降级成"看起来成功"；不把 0 读成"没有" |
| 5 | 审计先行 | 执行前写意图、执行后写结果；审计与业务同事务或 outbox，不丢 |
| 6 | 幂等默认 | 所有写动作带 `idempotency_key`；重复请求返回首次结果，不重复执行 |
| 7 | 可观测 | 每个动作一个 span；`control_action_ms`、`alert_delivery_ms`、`ack_latency_ms` 进 Tracer |
| 8 | 先加后删 | 新路径上线并跑通后，再删旧路径；删除前用调用图确认零消费者 |

### 0.3 质量门禁

| 层 | 门禁 |
| --- | --- |
| 后端 | `ruff format --check`、`ruff check`、`mypy src/aegis`、全量 `pytest`、`vulture`（死代码） |
| 前端 | `typecheck`、`lint`、`format:check`、`vitest`、`build`、`ts-prune`（未使用导出） |
| 端到端 | `e2e/ui-overlap` + 新增 `e2e/assistant-dock`、`e2e/alert-flow` |
| 契约 | OpenAPI 快照对账；SSE 帧类型快照对账 |
| 变异 | 权限判定、幂等、影响预览、审计四处各至少一条变异必须变红 |

## 1. 架构

### 1.1 分层视图

```
┌─ L5 交互层（Vue）
│   AssistantDock → AssistantPanel → AlertStack / Conversation / HandlingBar
│   api/assistant.ts（对话与动作）  api/alerts.ts（告警）  api/spaces.ts（协同）
├─ API 层（FastAPI）
│   api/assistant_api.py   对话、能力面、动作确认/撤销
│   api/routers/alerts.py  告警查询与确认
│   api/routers/spaces.py  处置空间与任务
│   api/routers/stream.py  事件流（新增 alert/handling subject）
├─ 应用服务层
│   services/assistant/service.py   门面：对话编排
│   services/assistant/executor.py  统一执行器（八步）
│   services/assistant/registry.py  动作注册表
│   services/assistant/actions/*.py 每个动作一个类
│   services/alerting/service.py    告警状态机、去重、升级
│   services/collab/service.py      空间、任务、认领/移交/回执
├─ 领域与基础设施
│   domain/（模型、枚举、状态机）
│   persistence/（Postgres、读视图回填）
│   bus/（NATS、事件广播）
│   observability/（Tracer、Prometheus）
└─ 既有业务服务（唯一真源，助手不复制）
    WarningService / WorkflowService / RuleService / DeliveryDispatcher / ReportIntake
```

### 1.2 模块职责（新建部分）

| 模块 | 职责 | 不做什么 |
| --- | --- | --- |
| `services/assistant/registry.py` | 登记动作、启动自洽校验、按角色过滤 | 不执行业务 |
| `services/assistant/actions/*` | 每个动作的参数、目标解析、影响预览、执行、撤销 | 不处理 HTTP、不写会话 |
| `services/assistant/executor.py` | 八步管线、幂等、限流、审计 | 不实现业务规则 |
| `services/assistant/intent.py` | 规则词表 + LLM 选动作 + 参数抽取 | 不判定权限 |
| `services/assistant/service.py` | 对话编排、帧序列、会话 | 不写业务表 |
| `services/alerting/service.py` | 告警从事件到确认/升级的状态机 | 不生成预警（那是 `WarningService`） |
| `services/collab/service.py` | 空间、任务、认领/移交/回执 | 不解析 STU（那是 `TaskParser`） |

### 1.3 为什么从 `interpret/assistant.py` 拆出来

现状：单文件 900+ 行，混合意图、执行、会话、叙述、越权闸；`AssistantActions` 是 11 个可空 callable 的 dataclass，靠 `container.py` 手工注入，新增动作要改三处。

拆分后：
- `interpret/` 保留 `semantic_parser.py`、`text_guard.py`（上报解析与数字闸，与助手无关）。
- 助手迁到 `services/assistant/`，按职责分文件；`AssistantActions` 这层"万能注入"删除，动作类直接依赖具体服务（构造注入），依赖关系显式。
- 迁移顺序见 §12：先抽 `models/registry`，再抽 `executor`，最后 `service` 变薄；每一步跑全量门禁。

### 1.4 与既有模块的边界

| 既有模块 | 助手如何用 | 禁止 |
| --- | --- | --- |
| 自研 DAG（19 类节点） | `workflow.start` / `workflow.decide` 调既有 `WorkflowService` | 不在助手内新建编排引擎 |
| 五智能体 + 总线 | 只读 `chain_runs` 与 `/agents` 状态；告警走既有广播 | 不新增智能体、不改 AgentMessage v1 |
| `WarningService` | 只负责生成（`generate`）；发布/撤回/改级由新抽出的 `WarningPublisher` 承担 | 不在 `WarningService` 里塞发布逻辑 |
| `WarningPublisher`（新） | 把 `HazardStages._execute` 的 `_dispatch` + `_broadcast` + 写读视图抽出；`HazardStages` 改为调用它 | 不复制触达与广播 |
| `DeliveryDispatcher` | 重发复用 `dispatch(record)`；通知走新 `Notifier`（站内 + 事件，不接外部通道） | 不绕过通道矩阵与白名单；不伪造 `WarningRecord` |
| `WorkflowEngine` | `workflow.start` → `start/start_from_name`；`workflow.decide` → `resume(instance_id, node_id, decision)`；`workflow.abort` → `abort` | 不新建编排引擎 |
| `ThresholdSuggestionService` | 确认/驳回复用现有 `confirm/reject` 与 409 语义 | 不直接改 `trigger_rules` 表 |
| `TaskParser` | 只读 STU；写状态落 `handling_tasks`，不改 STU 契约 | 不在 STU 上加 `assignee/status` 字段（契约不动） |

### 1.5 一次指令的完整调用链

```
前端 POST /assistant/chat
  → assistant_api.chat
    → AssistantService.respond
      → intent.classify（规则 → LLM → 回落）
      → registry.require(action)
      → executor.run
          1 parse:    spec.params.model_validate(raw)
          2 resolve:  action.resolve(params, ctx) → targets
          3 authorize:authorize(operator, spec) → 通过/拒绝
          4 preview:  action.preview(targets, params) → ImpactPreview
          5 gate:     needs_confirm ? 落库 proposed + proposal 帧 : 继续
          6 execute:  action.execute(targets, params, ctx) → ActionResult
          7 ack:      落库 executed + result
          8 audit:    audit_ops 写一行（含 utterance 与 resolved_args）
      → narrate（确定性叙述 + 数字闸）
      → SSE 帧：meta → intent → status → result → answer → done
```

关键点：**对话不直接执行写动作**。写动作在第 5 步落库为 `proposed`，由 `POST /assistant/actions/{id}/confirm` 推进；读动作可以一次走完。

## 2. 领域模型

### 2.1 对象清单

| 对象 | 载体 | 生命周期 | 说明 |
| --- | --- | --- | --- |
| `Operator` | `operators` 表 | 长期 | 席位：`operator_id`、`display_name`、`role` |
| `ActionSpec` | 代码注册表 | 进程 | 动作元数据：名字、域、角色、参数模型、是否确认、可逆 |
| `ControlAction` | `control_actions` 表 | 单次执行 | 一次动作请求：`action_id`、`status`、`resolved_args`、`result` |
| `Alert` | `assistant_alerts` 表 | 一次预警 | 告警实例：等级、区域、确认、升级、演练标识 |
| `HandlingSpace` | `handling_spaces` 表 | 一条预警 | `space_id = warning_id` |
| `HandlingTask` | `handling_tasks` 表 | 一个任务 | 受理人、状态、版本（乐观锁） |
| `AuditOp` | `audit_ops` 表 | 一次写操作 | 谁、说了什么、做了什么、前后值 |

### 2.2 状态机

**ControlAction**

```
proposed ──confirm──▶ executing ──ok──▶ executed
    │                     │
    │                     └──err──▶ failed
    ├──reject──▶ rejected
    ├──expire──▶ expired
    └──revoke──▶ revoked（仅 reversible 且未执行完）
```

**Alert**

```
raised ──push──▶ delivered ──ack──▶ acked
   │                 │
   │                 ├──timeout──▶ escalated ──ack──▶ acked
   │                 └──drill──▶ closed（不升级）
   └──dedup──▶ merged（同 trace_id）
```

**HandlingTask**

```
pending ──claim──▶ claimed ──start──▶ in_progress ──ack──▶ acked ──close──▶ closed
   │                  │
   │                  └──transfer──▶ pending（换受理人，version+1）
   └──assign──▶ claimed（派单直接指定受理人）
```

### 2.3 不变量（启动断言 + 测试钉住）

1. 同一 `action_id` 只能从 `proposed` 迁移一次，重复确认返回首次结果。
2. `executed` 的动作不可再转 `rejected/expired`；`revoked` 只能来自 `proposed/executing`。
3. 所有写动作必须有 `operator_id`，且该 operator 在 `operators` 表 `active=true`。
4. `space_id` 必须等于 `warning_id`；一个预警最多一个空间。
5. 同一 `trace_id` 的告警只保留一个 `raised` 记录，其余进 `merged`。
6. `handling_tasks.status` 的每次变更 `version+1`；更新必须带 `expected_version`。
7. `audit_ops` 只追加，不更新、不删除。
8. 演练告警的 `drill=true`，且不得产生 `escalated` 记录。
9. 任何动作不得直接写 `warnings`/`standardized_task_units`/`trigger_rules`，只能经既有服务。
10. `impact_scope` 在 `needs_confirm=true` 时不得为空。

## 3. 动作注册表

### 3.1 结构

```
services/assistant/
├── registry.py            # ACTIONS: dict[str, Action]；assert_consistent()
├── base.py                # Action 抽象基类、ActionContext、ActionResult
├── actions/
│   ├── query.py           # 读动作
│   ├── warning.py         # 预警控制
│   ├── task.py            # 处置任务
│   ├── workflow.py        # 工作流控制
│   ├── rule.py            # 规则/阈值
│   ├── drill.py           # 演练
│   ├── notify.py          # 通知
│   └── device.py          # 设备
```

注册表是**唯一动作目录**：`capabilities` 接口、意图校验、权限判定、测试全部读它。没有第二份清单。

### 3.2 `ActionSpec` 字段

| 字段 | 类型 | 必填 | 语义 |
| --- | --- | --- | --- |
| `name` | `str` | 是 | 唯一标识，`domain.verb`，如 `warning.publish` |
| `title` | `str` | 是 | 界面展示 |
| `domain` | `Literal` | 是 | `warning/task/workflow/rule/drill/notify/device/query` |
| `required_role` | `Role` | 是 | 最低角色（`duty`/`lead`/`admin`） |
| `params` | `type[BaseModel]` | 是 | 参数模型，`extra=forbid` |
| `needs_confirm` | `bool` | 是 | 是否二次确认（发布/批量/改规则/设备） |
| `reversible` | `bool` | 是 | 是否支持撤销窗口 |
| `idempotent` | `bool` | 是 | 是否接受 `idempotency_key` 去重 |
| `previewable` | `bool` | 是 | 是否生成影响预览 |
| `dual_review` | `bool` | 否 | 高安全档位下是否需要双人复核（默认 `False`）。只标在四类不可逆动作上；注册表校验要求它与 `needs_confirm` + `previewable` 同时为真，否则装配期启动失败 |

`Action` 基类方法：

```python
class Action(ABC):
    spec: ClassVar[ActionSpec]

    async def resolve(self, params: BaseModel, ctx: ActionContext) -> ResolvedTargets: ...
    async def preview(self, targets: ResolvedTargets, params: BaseModel, ctx: ActionContext) -> ImpactPreview: ...
    async def execute(self, targets: ResolvedTargets, params: BaseModel, ctx: ActionContext) -> ActionResult: ...
    async def revoke(self, action: ControlAction, ctx: ActionContext) -> ActionResult: ...  # 仅 reversible
```

### 3.5 参数模型规范

```python
class PublishWarningParams(BaseModel):
    model_config = ConfigDict(extra="forbid")
    warning_id: str = Field(pattern=r"^wrn_[0-9a-f]{8,24}$")
    reason: str = Field(min_length=2, max_length=200)
    channels: list[Channel] | None = None   # None = 用通道矩阵默认
```

规则：
- 每个动作一个模型，禁止复用大杂烩 `dict`。
- 枚举用 `Literal`/`StrEnum`，不用裸字符串。
- 所有字符串有长度上限；所有列表有 `max_length`。
- **LLM 不生成 ID**：`warning_id`/`task_unit_id` 只能由目标解析器从上下文或查询结果得到。

### 3.6 目标解析器

`resolve()` 负责把"通麦镇那条"变成 `wrn_…`：

| 输入形态 | 解析方式 | 歧义处理 |
| --- | --- | --- |
| 明确 ID（`wrn_`/`trc_`/`stu_`） | 正则提取，直查 | 不存在 → `E_TARGET_NOT_FOUND` |
| 区域 + 等级/灾种 | `warning.list` 过滤 | 多条 → `E_TARGET_AMBIGUOUS` + 候选列表，前端反问一次 |
| "刚才那条"/"这个" | 会话上下文 `last_target` | 无上下文 → 反问，不猜 |
| 人名"老李" | `operators` 按 `display_name` 精确匹配 | 重名 → 候选列表 |

**解析器只读**，不产生副作用；解析结果写入 `control_actions.resolved_args`，审计可回放。

### 3.7 启动自洽校验

`registry.assert_consistent()` 在 `PlatformContainer` 装配时执行，失败即启动失败（与现有 `NodeRegistry.assert_consistent` 同口径）：

1. `name` 唯一且匹配 `^[a-z_]+\.[a-z_]+$`。
2. `params` 是 `BaseModel` 子类且 `extra="forbid"`。
3. `needs_confirm=True` 的动作 `reversible` 或 `previewable` 至少一个为真（否则确认没有信息量）。
4. `reversible=True` 的动作必须实现 `revoke`（否则撤销是假的）。
5. `dual_review=True` 的动作必须同时 `needs_confirm=True` 且 `previewable=True`（复核票挂在确认闸上；标在别处就是空旋钮）。
6. 每个 `required_role` 在 `Role` 枚举内。
7. 注册表非空；每个域至少一个动作（防止拼写错误的域被静默忽略）。

## 4. 统一执行器

### 4.1 八步管线

```python
async def run(action: Action, raw: dict, ctx: ActionContext) -> AsyncIterator[Frame]:
    params = action.spec.params.model_validate(raw)        # 1 parse
    targets = await action.resolve(params, ctx)            # 2 resolve
    authorize(ctx.operator, action.spec)                   # 3 authorize（失败即抛 E_ACTION_NOT_ALLOWED）
    preview = await action.preview(targets, params, ctx)   # 4 preview
    if action.spec.needs_confirm and not ctx.approved:     # 5 gate
        record = await repo.create_proposed(..., space_id=ctx.space_id)
        yield proposal_frame(record, preview)
        return
    result = await action.execute(targets, params, ctx)    # 6 execute
    await repo.mark_executed(record_id, result)            # 7 ack
    await audit.write(...)                                 # 8 audit
    yield result_frame(result)
```

### 4.2 双人复核（配置项，默认关）

> 实施校准（2026-11-08，P3 第二批）：本节是**设计承诺的落地形态**，与方案 §3.1 规则 3 / FR-4.4 一一对应。

- 配置项 `AEGIS_ASSISTANT_DUAL_REVIEW_ENABLED`，**默认 `False`**：关着就是 D5「指令即执行」逐字不变，
  操作者本人的一次确认即执行；助手不因此多一道审批、操作者也不因此少一项能力。
- 打开后只对注册表里 `ActionSpec.dual_review=True` 的动作生效——四类不可逆动作共 10 个：
  `warning.*` 五个（发布/撤销/改级/重发/静默）、`notify.group`（批量）、`rule.*` 三个、`device.control`。
- 状态机（`services/assistant/review.py` 策略 + 台账原子迁移）：
  `proposed →(第一票 1/2) proposed →(第二票 2/2) executing`。
- 投票资格由 `ReviewPolicy` 一处判：复核席位取「`lead` 与动作自身 `required_role` 的更严者」，
  `duty` 点击被拒（`E_ACTION_REVIEW_FORBIDDEN`，403）并留痕；同一席位投第二票是
  `E_ACTION_DUPLICATE_REVIEW`（409），不是含混的"没抢到"。
- 两票落库在**同一条** `UPDATE ... WHERE status='proposed' AND NOT EXISTS(同人票) ... RETURNING`：
  两个值班长同时点第二票，行锁让后一个落空，只会执行一次。
- 台账列（012）：`control_actions.review_required`（0/2）与 `reviewers jsonb`（`[{operator_id, role, at}]`）；
  `confirm_action` 带复核票数闸，单票从任何路径都不能把状态推到 `executing`。
- 前端同步：能力面 `dual_review_enabled` + 动作清单每项 `dual_review`；`proposal` 帧带
  `review_required/reviews`，提案卡显示「双人复核 n/2」；`confirm` 返回新分支 `awaiting_review`
  （第一票已记、动作未执行，卡片仍可再点）。

### 4.3 失败语义与错误码

| 阶段 | 失败 | 错误码 | HTTP | 副作用 |
| --- | --- | --- | --- | --- |
| parse | 参数不合模型 | `E_ACTION_PARAM_INVALID` | 422 | 无 |
| resolve | 找不到目标 | `E_TARGET_NOT_FOUND` | 404 | 无 |
| resolve | 多候选 | `E_TARGET_AMBIGUOUS` | 409 | 无（返回候选） |
| authorize | 角色不足 | `E_ACTION_NOT_ALLOWED` | 403 | 无（审计留痕） |
| preview | 预览生成失败 | `E_PREVIEW_FAILED` | 503 | 无 |
| execute | 业务拒绝 | 由业务错误码透传 | 4xx | 由业务服务决定 |
| execute | 业务异常 | `E_ACTION_EXECUTION_FAILED` | 502 | 回执 `failed`，审计留痕 |
| ack | 落库失败 | `E_ACTION_ACK_FAILED` | 500 | 不重试业务，标记 `unknown` 待对账 |

### 4.4 幂等

- 客户端生成 `idempotency_key`（UUID），同一次用户意图内复用。
- `control_actions.idempotency_key` 唯一索引；重复请求直接返回首次 `status/result`，不重复执行。
- 服务端兜底：`(operator_id, action, resolved_args_hash)` 在 60 秒内重复，返回首次记录并标 `replayed=true`。
- 外部副作用（触达）由业务服务的去重键兜底；助手不重复调用。

### 4.5 事务与 outbox

| 写操作 | 事务边界 |
| --- | --- |
| `control_actions` 状态迁移 | 单表单事务，`UPDATE ... WHERE status=...` 乐观锁 |
| `handling_tasks` | 单表单事务，`version` 乐观锁 |
| `audit_ops` | 与状态迁移同事务（**已实现**：SQL 侧同一 `conn.transaction()`，内存侧同语句追加）；跨库时走 outbox（当前部署 audit_ops 与 control_actions 同库，不触发） |
| 业务写（预警/工作流） | 交给业务服务自己的事务；助手不跨服务开事务 |

**outbox**：若审计与业务不同库，写 `outbox` 表由后台投递；同一库则直接同事务，不引入 outbox（避免过度设计）。

### 4.6 影响预览

`ImpactPreview` 字段：

| 字段 | 说明 |
| --- | --- |
| `targets` | 受影响对象（ID + 展示名） |
| `audience_count` | 受众数量（发布/通知） |
| `channels` | 通道列表（站内/短信/北斗/HTTP） |
| `irreversible` | 不可逆项列表 |
| `warnings` | 风险提示（如"该区域 10 分钟前已发布同等级预警"） |

预览由动作自己实现，执行器只负责携带与展示；**预览失败不阻断读动作，阻断写动作**。

### 4.7 二次确认与撤销

- `needs_confirm=true`：创建 `proposed` 记录，返回 `proposal` 帧（含 `action_id`、`preview`、`expires_in_seconds`）。
- 确认：`POST /assistant/actions/{id}/confirm`，`UPDATE ... WHERE status='proposed'`，只有一个请求成功。
- 过期：`expires_at` 默认 300 秒；`maintenance.py` 每分钟执行 `UPDATE ... WHERE status='proposed' AND expires_at < now()`（多副本幂等）。
- 卡死恢复：启动时把 `status='executing' AND updated_at < now() - interval '10 minutes'` 标为 `failed`，`error.code='process_restart'`。
- 撤销：`reversible=true` 且 `status in (proposed, executed)` 且距执行 ≤60 秒；调用 `action.revoke()`；写 `revoked` + 审计。
- 不可逆动作（`rule.update`、`device.control`）不提供撤销按钮，预览里明确写"不可撤销"。

### 4.8 限流与熔断

| 维度 | 阈值（默认，可配） | 行为 |
| --- | --- | --- |
| 单会话写动作 | 10 次/分钟 | `E_ACTION_RATE_LIMITED`，提示等待 |
| 单操作者批量 | 50 个对象/次 | 拒绝并提示拆分 |
| 连续失败 | 3 次/分钟 | 熔断 60 秒，只允许读动作 |
| 告警风暴 | 同区域 60 秒 >5 条 | 折叠为一条汇总卡 |

### 4.9 审计

`audit_ops` 每行记录：`operator_id`、`role`、`action`、`target`、`before`、`after`、`utterance`（指令原文）、`resolved_args`、`idempotency_key`、`ts`。只追加，不更新。

读接口不写审计；写动作在**执行前**写一条 `phase='intent'`、**执行后**写一条 `phase='result'`（两条共用 `action_id`），保证"想做但失败"也有账。
两条都只追加；`control_actions.status` 才是当前态，审计是流水，两者职责不混。

> **实施校准（2026-11-08，第 8 步已接线）**：上面这段已落地，行形状唯一真源是
> `storage.store.AuditRecord`，写入唯一出口是 `services/assistant/audit.py::AuditTrail`：
> - **带确认闸的写动作**：intent 行随 `create_action` 与 `proposed` 落库**同事务**
>   （SQL 侧同一 `conn.transaction()`，内存侧同语句追加）；确认执行后 result 行随
>   `mark_executed` / `mark_failed` 同事务——迁移没命中（0 行）就不写审计，两条永远成对；
> - **无确认闸的写动作**（认领/回执/关闭/单发通知）：执行器在执行前补 intent 行、执行后补
>   result 行，关联键由审计自己生成（这类动作没有 `control_actions` 行）；
>   且**没有动作台账就不执行**——不存在"跑了但没记"的路径；
> - **越权**：角色不足/复核资格被拒只写一行 result（`after.rejected`=错误码），匿名尝试记
>   `operator_id='unknown'`；幂等重放不补行（重复提交不是新意图）；撤销成功补一行
>   `after={"revoked": true}`；
> - `before` 暂空：动作级的前值快照留给以后按需补（业务服务不回吐前值，不为审计再造一套
>   读前态链路）；`after` 记结构化结果/错误。读侧查询端点属 P4 读面需求，需要时再加。

### 4.10 可观测

- 每个动作一个 span：`assistant.action.{name}`，属性含 `operator_role`、`target_count`、`needs_confirm`、`status`。
- 指标：`assistant_action_ms{action,status}`、`assistant_confirm_ms`、`alert_delivery_ms`、`ack_latency_ms`。
- 日志：只记 `action_id`、`operator_id`、`status`，不记原文（原文在审计表，按权限读）。

### 5.2 请求/响应模型

```python
class ChatRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    message: str = Field(min_length=1, max_length=2_000)
    session_id: str | None = Field(default=None, pattern=r"^[A-Za-z0-9_-]{4,64}$")
    context: ChatContext | None = None      # route, selected_id, space_id
    idempotency_key: str | None = Field(default=None, max_length=64)

class CreateActionRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    action: str
    params: dict[str, Any]                  # 由 action.spec.params 校验
    context: ChatContext | None = None
    idempotency_key: str = Field(min_length=8, max_length=64)

class ActionView(BaseModel):
    action_id: str
    action: str
    status: Literal["proposed","executing","executed","failed","rejected","expired","revoked"]

    result: dict[str, Any] | None
    error: ActionError | None
    expires_at: str | None
```

`params` 在边界层是 `dict`，但**进入动作前必须转成 Pydantic 模型**；禁止把 `dict` 传给业务服务。

### 5.4 并发与幂等头

- `Idempotency-Key`：写动作必带；服务端落 `control_actions.idempotency_key`。
- `If-Match` / `expected_version`：任务移交与规则确认复用现有 409 语义。
- 告警确认：`POST /alerts/{id}/ack` 带 `expected_status`，重复确认返回 200 + `already=true`，不报错（避免值班员重复点）。

### 5.5 鉴权与席位

- 沿用 `AEGIS_SERVICE_TOKEN` 中间件（`api/app.py:90-116`）。
- 新增 `X-Aegis-Operator` 头：`operator_id`（4–32 位字母数字）；后端查 `operators` 表，不存在或停用 → `E_OPERATOR_INVALID`。
- 读动作允许匿名（记 `unknown`）；写动作必须有席位且 `active=true`。
- 席位是**声明身份**，不替代认证；审计里写 `identity_kind=declared`。
- 角色判定只在 `authorize()` 一处；路由层不做角色判断（避免两套）。
- `GET /operators/me` 缺席位头时返回 `{operator_id:null, role:null}`（200），让前端区分"没选席位"与"席位无效"。
- 越权匿名：`audit_ops.operator_id` 允许写 `unknown`，该列**不加 FK**；`control_actions.operator_id` 仍要求有效席位（写动作不成立就不落执行记录）。

### 5.6 SSE 帧扩展

现有 9 帧全部保留；新增 2 帧：

| 帧 | 字段 | 触发 |
| --- | --- | --- |
| `preview` | `action_id`、`targets`、`audience_count`、`channels`、`irreversible` | 写动作进入 `proposed` 前 |
| `plan` | `steps[]`（`action`、`reason`、`resolved`） | 多步指令 |

`proposal` 帧扩展：`required_role`、`preview`、`expires_in_seconds`（已有）；P3 第二批再加
`review_required` / `reviews`（双人复核档的票数与已收票，缺省 0/[] 表示本人一次确认）。

前端同步：`AssistantFrame` 联合类型、`QUIET_TYPES`、`frameText` 必须同时加 `preview` / `plan` 分支；
漏加会让新帧落到 `frameText` 的默认分支返回 `undefined`，界面上出现一句空白。
`preview` 归入 `QUIET_TYPES`（过程帧），`plan` 不折叠（用户要看步骤）。

### 5.7 契约影响

`contracts/agent_message.v1.schema.json` 不动。人的动作走 REST + `audit_ops`；事件流新增 subject 不改变 `AgentMessage` 结构。若未来要让智能体感知"人已接手"，另立 v2，不在本期。

## 7. 数据模型与迁移

### 7.1 新表

```sql
CREATE TABLE operators (
  operator_id   text PRIMARY KEY,
  display_name  text NOT NULL,
  role          text NOT NULL CHECK (role IN ('duty','lead','admin')),
  active        boolean NOT NULL DEFAULT true,
  created_at    timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE control_actions (
  action_id       text PRIMARY KEY,
  operator_id     text NOT NULL REFERENCES operators(operator_id),
  action          text NOT NULL,
  space_id        text,
  utterance       text NOT NULL DEFAULT '',
  resolved_args   jsonb NOT NULL DEFAULT '{}',
  status          text NOT NULL CHECK (status IN ('proposed','executing','executed','failed','rejected','expired','revoked')),
  idempotency_key text UNIQUE,
  impact_scope    jsonb NOT NULL DEFAULT '{}',
  result          jsonb,
  error           jsonb,
  expires_at      timestamptz,
  created_at      timestamptz NOT NULL DEFAULT now(),
  updated_at      timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE assistant_alerts (
  alert_id      text PRIMARY KEY,
  warning_id    text NOT NULL,
  level         int  NOT NULL,
  region_code   text NOT NULL,
  status        text NOT NULL CHECK (status IN ('raised','delivered','acked','escalated','merged','closed')),
  ack_by        text REFERENCES operators(operator_id),
  ack_at        timestamptz,
  assigned_to   text REFERENCES operators(operator_id),
  snooze_until  timestamptz,
  escalated_at  timestamptz,
  drill         boolean NOT NULL DEFAULT false,
  created_at    timestamptz NOT NULL DEFAULT now(),
  UNIQUE (warning_id)
);

CREATE TABLE handling_spaces (
  space_id   text PRIMARY KEY,
  warning_id text NOT NULL UNIQUE,
  status     text NOT NULL CHECK (status IN ('open','closed')),
  created_at timestamptz NOT NULL DEFAULT now(),
  closed_at  timestamptz
);

CREATE TABLE handling_tasks (
  task_id    text PRIMARY KEY,
  space_id   text NOT NULL REFERENCES handling_spaces(space_id),
  stu_id     text NOT NULL,
  assignee   text REFERENCES operators(operator_id),
  status     text NOT NULL CHECK (status IN ('pending','claimed','in_progress','acked','closed')),
  version    int  NOT NULL DEFAULT 1,
  updated_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (space_id, stu_id)
);

CREATE TABLE audit_ops (
  id              bigserial PRIMARY KEY,
  action_id       text NOT NULL,
  phase           text NOT NULL CHECK (phase IN ('intent','result')),
  operator_id     text NOT NULL,
  role            text NOT NULL,
  action          text NOT NULL,
  space_id        text,
  target          text NOT NULL DEFAULT '',
  before          jsonb,
  after           jsonb,
  utterance       text NOT NULL DEFAULT '',
  resolved_args   jsonb NOT NULL DEFAULT '{}',
  idempotency_key text,
  identity_kind   text NOT NULL DEFAULT 'declared',
  ts              timestamptz NOT NULL DEFAULT now()
);
```

说明：
- `assistant_alerts.level` 存 `int(risk_level)`：`RED=1 / ORANGE=2 / YELLOW=3 / BLUE=4`，界面 Ⅰ–Ⅳ 与之一一对应（数值越小越严重）。
- `ack_by` 是"确认人"，`assigned_to` 是"当前处置人"（转派只改后者），`snooze_until` 是稍后提醒截止；三个字段语义不混。
- `handling_tasks.stu_id` 是逻辑外键（不加 FK）：STU 可能在只读/内存形态，不把两域绑死。
- `control_actions.action` 是动作名（`domain.verb`），不是 SQL 关键字冲突。
- `operators` 不在迁移里插默认账号；由 `scripts/seed_operators.py --file operators.json` 或 `POST /operators` 初始化，避免生产出现默认管理员。
- `audit_ops.operator_id` 不加 FK（越权匿名写 `unknown`）；`control_actions.operator_id` 加 FK（写动作必须有有效席位）。
- `assistant_alerts` 由各实例并发写入，`UNIQUE (warning_id)` + `ON CONFLICT DO NOTHING` 保证多副本只留一条。

| "抽出 `WarningPublisher`" | `pipeline/publisher.py::WarningPublisher`，方法为 `release / publishable / resendable / mark_revoked / change_level` | 架构铁律的 AST 门禁禁止 `services/` import `aegis.bus`；发布必须广播，只能落在 `pipeline/`。动作层用 `PublisherPort` Protocol 反向注入，不依赖 pipeline |
| "三条发布入口" | `HazardStages._execute`、`workflow/services_bridge.py::publish_warning`、`actions/warning_control.py` 都调 `release()` | 工作流画布原先只 dispatch 不广播，助手若再写一份就是第三条语义 |
| "写读视图抽到 Publisher" | **未抽**：Publisher 不读写存储；主链路写段缓存，工作流与助手写 `store.warnings` | Publisher 反握 `WarningPort` 会让主链路那条只写段缓存的路径无从装配 |
| `Notifier` 发 `notify.*` 事件 | `services/alerting/notifier.py`，事件名 `Action.NOTIFY_SENT.value == "notify.sent"`，主题 `ops.assistant.notify`，`publish` 回调注入 | 同上 AST 门禁；SSE 把 `message.action` 作为 `subject` 推前端，故前端按 `notify.sent` 分流 |
| `container.py::_record_chain` | 实际函数名为 `container.py::on_result`；`store.record_chain(result)` 后直接 `collab.ensure_from_chain(result)` | 单一落库点，链路一落地就能被认领，不靠定时任务补 |
| 通知存储 | `assistant_notifications` 表 + `NotificationStore`（内存），`SupportsNotifications` | 站内通知是人对人的一句话，不能复用 `assistant_alerts`（按 `warning_id` 去重），更不能伪造 `WarningRecord` |
| 撤销状态 | `WarningRecord.revoked_at` + 派生 `status` property；`rows.warning_status()` 只转发 | 只允许一个状态真源；`released_at` / `deliveries` 不改写 |

## 8. 关键时序

### 8.1 发布预警（L3）

```
操作者(lead) 说"把通麦镇这条发出去"
→ chat: intent=warning.publish, resolve→wrn_8f2c, authorize→通过
→ preview: 受众 3 村 / 通道 2 条 / 不可逆=false
→ control_actions(proposed) + proposal 帧
→ 操作者点"确认发布"
→ POST /actions/{id}/confirm（If-Match: status=proposed）
→ WarningPublisher.publish(record, operator)
→ 触达 DeliveryDispatcher.dispatch
→ 总线广播 platform.alert.2.<region>（payload 新增 `drill: bool`，由链路来源判断）
→ control_actions(executed) + audit_ops(result)
→ 空间与任务由 `container._record_chain` 调 `CollabService.ensure_from_chain` 统一 upsert，本流程不重复建
→ SSE result 帧 + 前端回执
```

### 8.2 告警送达与确认

```
总线 platform.alert.> → 两个独立订阅者，互不依赖：
  ① stream.py 推帧给前端（payload 含 drill：本次链路读数全部来自 simulator 即演练）
  ② AlertingService：INSERT INTO assistant_alerts ... ON CONFLICT (warning_id) DO NOTHING
     —— 初始状态 raised；预警行不在时列表 LEFT JOIN 返回空串（"未取到"），不省略字段
→ useEventStream → useAlerts 按 subject 分流（seen 集合按 warning_id 去重）
→ AlertStack 插入卡片（Ⅰ/Ⅱ 自动展开 + 顶部条；Ⅲ 展开；Ⅳ 仅角标）
→ 操作者点"接手" → POST /alerts/{id}/ack（duty+；重复确认 200 + already=true）
→ assistant_alerts(status=acked, ack_by, ack_at, assigned_to=COALESCE(assigned_to, operator))
→ 操作者点"转派" → POST /alerts/{id}/transfer → 只改 assigned_to（lead+；ack_by 不覆盖）
→ 操作者点"稍后" → POST /alerts/{id}/snooze → 只改 snooze_until（不隐藏，仍留痕）
→ 超时未确认 → 定时任务执行**原子 UPDATE**：
   `UPDATE assistant_alerts SET status='escalated', escalated_at=now()
    WHERE status IN ('raised','delivered') AND drill=false
      AND created_at < now() - interval '<escalation_minutes>'
      AND (snooze_until IS NULL OR snooze_until < now()) RETURNING alert_id`
→ 只有 `RETURNING` 到行的实例发通知（多副本天然幂等，不靠单实例锁）
```

> 与初稿的差异（实施时修正）：升级源状态是 `('raised','delivered')` 而不是只有 `delivered`——
> 站内告警没有独立"送达回执"，插入即 raised，若只等 delivered 就永远不会升级。
> `snooze_until` 到期即升级（稍后是推迟，不是取消）。

### 8.3 多人认领（乐观锁）

```
A: POST /spaces/{id}/tasks/{tid}/claim (expected_version=1)
B: POST /spaces/{id}/tasks/{tid}/claim (expected_version=1)
→ 先到者 UPDATE ... WHERE version=1 → version=2, assignee=A
→ 后到者 0 行受影响 → 409 E_TASK_STATE_CONFLICT，返回当前受理人
```

### 8.4 多步指令

```
"先核签，再发布，然后通知下游"
→ chat 返回 plan 帧：steps[3]，每步含 action/reason/resolved
→ 前端逐条 POST /actions（每步一个 action_id）
→ 步骤 1 成功 → 步骤 2 提案 → 确认 → 执行
→ 任一步失败：停止后续，保留已完成结果，界面标"停在第 2 步"
```

### 8.5 撤销

```
"刚才那条撤回"
→ resolve→action_id（会话 last_action）
→ 校验 status=executed 且 now-created_at ≤60s
→ action.revoke()（WarningPublisher.revoke）
→ control_actions(revoked) + audit_ops
→ 超过窗口：409 E_ACTION_CONFLICT，提示走正式撤回流程
```

| 失败 | 行为 |
| --- | --- |
| LLM 不可用 | 规则词表仍可识别已登记动作；`capabilities.llm_configured=false`；不臆造动作 |

| 幂等重放 | 返回首次结果 + `replayed=true`；不重复副作用 |
