# ADR-0016：统一智能体层与能力矩阵

- 状态：已采纳（2026-11-11）
- 关联：ADR-0011（外部模块并入）、ADR-0012（assess 契约统一）、ADR-0013（LLM 熔断与客户端复用）、ADR-0015（REST 客户端复用与有界副本）

## 背景

灾种闭环模块（原 `agents_ext`，并入自 hazard-landslide-agent）并入后，平台长期处于
"两套系统"状态：自建五段内环是一套，灾种模块是另一套——六个 agent 里只有研判一个
注册上总线，其余五个是裸函数返回 dict；闭环对兄弟的调用走进程内直调，绕过消息信封、
deadline、幂等与错误分类；监督工具（契约门禁、边界守卫）三处并存、宽严不一；
LLM 通路、配置、prompt、测试夹具各两套。

用户目标：**完全合并成一套高性能、高质量、无死代码、规范统一的系统**；统一后的
测试/审计文件取更严格的那一方。

## 决策

### 1. 一套智能体层：11 个本体、一张能力矩阵

- 平台自建五段（perceive/assess/plan/execute/feedback，`.real01`）+ 灾种六体
  （data01/factor01/sim01/hazard01/audit01/loop01）**同挂一条总线**。
- **能力矩阵**（`backend/src/aegis/agents/capabilities.py`）是单一真源：
  capability（路由键）、action（语义动词）、owner（承接本体）、dispatched（平台会不会派单）
  四元组一处登记。总线路由键是 `(agent_type, capability)` 而非 action，因此
  **每项能力恰好一个主人**——两个本体声明同一能力，`registry.pick()` 按负载取舍，
  "谁应答"变成随机数。
- **不存在实现选择开关**：`AEGIS_AGENT_IMPL` 删除；`AEGIS_AGENT_RUNTIME=real` 时
  11 个本体一并装配，灾种 extra `agents` 未装时如实留痕跳过。

### 2. 闭环内部也走总线

`manager_agent` 对五条腿的派单改为**总线请求**（`bus_context.py`）：
兄弟本体可跑在别的进程；每次调用有信封级观测；失败走平台统一错误分类。
闭环图是同步的（LangGraph 节点在 executor 线程），总线请求经
`run_coroutine_threadsafe` 桥回平台事件循环，并带**重入守卫**（循环线程内调用当场拒绝）。

### 3. 执行器拓扑：编排与腿物理隔离

闭环编排器与五条腿**不得共用一个线程池**（池容量 1 时确定性死锁——编排器占住唯一
worker、腿永远排队）。编排器自带专用执行器（`workflow_workers`），腿共享
`AEGIS_HAZARD_POOL_WORKERS` 池；外层 `deadline_ms` 作为闭环总预算向下传导
（单腿 = min(单腿上限, 剩余/5)，耗尽快速失败）。

### 4. mock 拓扑与生产同构

mock 替身按能力矩阵拆成**一项能力一个本体**（编号按矩阵序，主能力仍在 `.mock01`）。
一项能力一个本体，`max_concurrency` 才按"一个逻辑智能体一份"记账——否则并行腿会
把自己的主腿挤到饱和（实测复现的拓扑伪影）。

### 5. 监督工具取严者、集中一处

- **数据边界守卫的唯一真源**：`tests/unit/test_hazards_boundaries.py`——全域档
  （agents/** 禁 DB 驱动/存储层/sys.path/明文密钥）+ 灾种加严档升级为**白名单制**
  （对 `aegis.*` 的依赖只许契约面与自己的包，默认拒绝）。此前三处静态扫描
  （两份 conformance 的 Gate6 + 本文件）各有别人没有的牙、且宽严互相矛盾——
  统一后两份 conformance 的 Gate6 只保留运行时实例断言。
- **能力矩阵门禁**（`tests/unit/agents/test_capability_matrix.py`）：每项能力
  恰好一个主人；`dispatched=True` 必须有真实派发点（源码扫描 stages/路由层）；
  `dispatched=False` 必须可归属（闭环五腿或本体自发事件）；派发点不得用矩阵外的能力。

### 6. 已知取舍

- **LLM 通路维持两套**（平台 `services/llm` vs 灾种 `hazards/llm.py`）：
  平台侧有用量台账/prompt 版本化/多模型路由，灾种侧有带恢复窗口的熔断。
  硬合要重写 136 个文件的 prompt 层，收益不抵风险；列为后续项
  （灾种侧 `llm_breaker.py:22-24` 自述了"改走平台网关即可整体删除"的条件）。
- **灾种 prompt 无版本号**、不进平台台账——同上，属后续项。
- **操作审计与链内审计是两个概念**，不合并：前者审计操作者动作
  （`api/routers/audit.py`），后者审计闭环交付物自洽性（`chain_audit`），
  输入输出零重叠。

## 后果

- 正面：智能体层从"两套并行 + 一根线"变成"一套总线 + 一张能力矩阵"；
  监督工具单一真源、取严者；闭环可观测（每条腿有信封级记录）；
  六体的六个能力全部有真实派发点或事件腿出处。
- 代价：灾种模块的 `print` 全量转 logging（约 100 处）；mock 拓扑变更使
  在线替身数从 5 变 12（相关断言同步）；`AEGIS_EXT_*` 环境变量族名暂未改
  （部署面契约，改名需迁移通知，列为后续项）。

## 实测证据

- 全量 4270+ 用例通过（能力矩阵门禁、白名单边界、生产路径闭环回归在内）；
- 闭环五腿经总线跑通（`test_hazard_closed_loop.py`：订阅总线收集上行消息，
  断言五步都发往兄弟本体的专属收件箱——进程内直调不会在总线上留痕）；
- 池容量 1 的腿池上闭环完整跑通（`test_生产路径闭环在容量1的腿池上不死锁`）；
- 能力矩阵门禁自己抓出过两个真缺陷：`perceive.trigger_hit` 事件腿无发出点、
  因子引擎与主研判曾声明同一能力。
