# ADR-0013：外部实现 LLM 的熔断与客户端复用——让"上游坏了"变成毫秒级降级，而不是三秒等待

- 状态：已采纳（2026-11-10）
- 日期：2026-11-10
- 相关：ADR-0002（智能体优先、平台降级）、ADR-0011（外部模块并入方式）、
  ADR-0012（研判契约统一）、`docs/architecture.md` §3.1、
  `docs/REPORT.md`（本 ADR 的数字都在 REPORT 里有原始取证）
- 涉及代码：`backend/src/aegis/agents_ext/llm.py`、`backend/src/aegis/agents_ext/llm_breaker.py`、
  `backend/src/aegis/agents_ext/config.py`

## 背景

外部实现（`agents_ext`）的研判段调 LLM 做**解释**（定级与数值全部来自确定性的因子引擎）。
一次研判要调两次 LLM（解释段 + 验证段）。

2026-11-10 剖析这条链路时量到（`scripts/bench_assess_ext.py`，上游真实返回 5xx）：

- 单次研判中位 **2952 ms**（改造前同口径复测值；首轮测得 3129 ms）；
- 10 轮共 32.5 s 里，**26.3 s（81%）** 是 `openai/_base_client.py::_sleep_for_retry`
  的指数退避 `time.sleep`，6.2 s 是 SSL 读，纯 CPU 计算不到 0.5%。

也就是说：**这条链路的耗时几乎全部是"等一个已经坏了的上游"**，不是计算。

## 问题

### 1. SDK 的盲重试把一次逻辑调用变成三次 HTTP 往返

`openai` SDK 默认 `max_retries=2`，对 5xx / 429 / 连接错误自动重试，
退避 0.5 s → 1.0 s（`_calculate_retry_timeout`，`INITIAL_RETRY_DELAY=0.5`）。

盲重试本身不是错——它救的是"偶发抖动"。错的是**它没有记忆**：
上游持续不可用时，每一次调用仍然要付满三次往返 + 1.5 s 退避，
而节点早就有确定性兜底在等着。于是链路吞吐被拖垮：
**每次请求都在为"它反正会失败"付三次网络往返的钱。**

### 2. 每次调用新建 client（`get_llm()` 每次都 `return ZhipuCompatChatOpenAI(...)`）

两个后果：

- 每次新建要走一遍 pydantic 校验 + `openai.OpenAI` 包装层构造，实测 **0.26 ms/次**；
- 更要紧的：**熔断器必须挂在 client 实例上**。若每次新建 client，
  连续失败计数就永远归零——熔断根本打不开。

> **一处必须写清的误判**：改造前我以为"每次新建 client → 每次新建 httpx 连接池 →
> 每次 TLS 握手"。**实测不是**：langchain 的 `_get_default_httpx_client` 按
> `(base_url, timeout, socket_options)` 缓存并共享 httpx 客户端
> （实测两个独立 client 的 `root_client._client` 是同一对象）。
> 所以复用的收益**不是**省 TLS 握手，而是省构造开销 + 让熔断账能跨调用累积。
> 这条已按实测改正，注释里也改了。

## 决策

### 1. 熔断（`agents_ext/llm_breaker.py`）

`closed →（连续失败达阈值）→ open →（冷却窗口到期）→ half_open →（试探成功）→ closed`。

- **记账口径**：只记"服务不可用"——连接错误、超时、5xx、429。
  4xx（除 429）**不记**：Key 错、参数错、模型名错，重试多少次都一样，
  记进去只会让一个本该立刻暴露的配置错误被一段冷却期糊过去。
  语义错误（模型返回非法 JSON）也不记——那是提示词问题，不是服务不可用。
- **半开只放行一次试探**：恢复瞬间不该被并发打穿；也不是彻底封死，否则恢复不了。
- **状态是进程内的**：多副本各自计数。平台网关的熔断也是进程内的，同一取舍。

### 2. 平台网关的熔断口径**不**照抄

`aegis/services/llm/llm_gateway.py` 的熔断**没有恢复窗口**：模型失败达阈值就永久跳过它，
靠 fallback 模型接力。外部实现**只有一个模型**，照抄那条口径会让熔断变成永久失效——
上游恢复了也永远用不上。所以外部实现自带冷却窗口（默认 60 s）。

两份熔断并存不是重复实现：外部模块**不得依赖平台内部实现**
（`tests/unit/test_agents_ext_boundaries.py` 把 `aegis.services` 列为禁止依赖）。

### 3. 关掉 SDK 盲重试（`max_retries=0`）

盲重试是实测里 81% 的时延来源，而熔断已经接管了"上游坏了"的判断：
熔断窗口内一次 HTTP 都不发，**比盲重试更快也更诚实**（不假装还在努力）。
韧性没有因此下降：偶发抖动由节点既有兜底接住（模板说明 / 规则判断），结论不丢。

可通过 `AEGIS_EXT_LLM_MAX_RETRIES` 调回（默认 0）。

### 4. 客户端进程级复用

按 `(模型, 端点, 凭据指纹, 重试次数)` 缓存。**凭据用 SHA-256 指纹入键**：
指纹够用（Key 换了 → 指纹变 → 建新实例），且明文凭据不会留在任何会被日志带走的结构里。

### 5. 检查点选在 `_generate`，**不是** `get_llm()`

这是本次改造里最容易做错的一处：

`risk_assess_node` / `risk_validate_node` 里 `get_risk_llm()` 是在 `try` 块**之外**调用的。
若在工厂里抛"LLM 不可用"，异常会冲掉节点既有的"模板兜底"契约——
**节点会整个失败，而不是降级出模板说明**。这是语义回归，比慢更糟。

放在 `_generate`（本类的薄适配层）里抛，异常落在节点的 `try` 内，
**兜底行为逐字不变**：LLM 不可用 → 模板说明 / 规则兜底，`risk_level` 仍来自因子引擎。

## 后果

**好的**：

- 上游不可用时，研判链路从"每次白等三秒"变成"毫秒级确定性降级"：
  中位 **2952 ms → 4.14 ms**（713×），吞吐 0.3 → 241 次/秒；
- 上游健康时也不退步：客户端复用省下构造开销，中位 **11.08 ms → 9.34 ms**（1.19×，
  本地假 OpenAI 兼容端点实测，`scripts/bench_assess_llm_healthy.py`）；
- 节点既有兜底契约逐字不变（有测试钉住，见下）；
- 熔断是纯逻辑、无 IO、可直接单测的独立文件。

**要付的代价**：

- 多一份熔断状态（进程内，多副本各自计数）；
- 熔断打开期间，LLM 解释**一律拿不到**（此前每次都可能拿到）——
  这是有意的取舍：宁可给模板说明，不要每次白等三秒；
- `AEGIS_EXT_LLM_MAX_RETRIES` 默认从 SDK 的 2 变成 0：上游偶发 5xx 时，
  那一次研判会走模板兜底而不是重试成功。窗口内由熔断负责恢复。

**明确不做**：

- 不让外部实现的 LLM 改走平台网关（`llm_gateway` 是 async 契约，外部实现是同步调用，
  且边界守卫禁止外部模块依赖 `aegis.services`）——另立一项；
- 不做熔断状态的跨副本共享（Redis 等）——另立一项；
- 不改节点的兜底逻辑本身（模板说明 / 规则判断一个字没动）。
