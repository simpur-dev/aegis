## 二、目标架构总览与论文对齐

### 2.1 总体架构（五层 + 一基座 + 一张图 + 一总线）

```
┌────────────────────────────────────────────────────────────────────┐
│  L5 应用层  │  态势大屏(一张图) / 预警门户 / 任务调度台 / 会商研判 / 群防群治上报(Web) │
├────────────────────────────────────────────────────────────────────┤
│  L4 服务层  │  任务编排服务 / 智能解析服务 / 协同调度服务 / 预警生成服务 │
├────────────────────────────────────────────────────────────────────┤
│  L3 智能层  │  感知智能体 │ 研判智能体 │ 决策智能体 │ 执行智能体 │ 反馈智能体 │
│             │  ←—— 智能体消息总线 (NATS JetStream) ——→              │
├────────────────────────────────────────────────────────────────────┤
│  L2 数据层  │  多源感知数据 │ 灾情知识图谱 │ 历史案例库 │ 工作流定义库 │ 预警规则库 │
├────────────────────────────────────────────────────────────────────┤
│  L1 感知层  │  卫星遥感 │ InSAR │ 雨量/水位/泥位 │ 视频监控 │ 群防群治上报 │
├────────────────────────────────────────────────────────────────────┤
│  基座层     │  通信网关(弱网) │ 边缘计算节点 │ 安全认证 │ 时空基准 │ LLM认知中枢 │
└────────────────────────────────────────────────────────────────────┘
```

**应用形态定案：纯 Web 平台（响应式，不做原生移动端）**。架构设计文件 L5 中的"联动处置 App / 移动巡检 App"由响应式 Web 页面（移动浏览器可用）承载：现场人员经浏览器完成巡检上报、指令接收与反馈，群防群治上报为 Web 表单页。触达渠道（短信/北斗/应急广播/微信消息推送）属于消息通道而非应用端，予以保留。

业务主闭环采用"四预"：**预报**（多源数据风险预测）→ **预警**（规则+模型分级预警）→ **预演**（数字孪生态势推演）→ **预案**（柔性工作流编排处置）→ 反馈反哺，与课题"感知—研判—决策—执行—反馈"全链条一一对应。

### 2.2 与导师论文 MA-RIAEW 的逐层映射

| 本课题架构 | 论文对应子系统/模块 | 对齐要点 |
|---|---|---|
| L1 感知层 + 统一接入网关 | 智能体管理中心 · 环境感知模块 | 物理环境/网络空间/沙盒环境信息的感知与处理 |
| L2 数据层 | 数智底座 · 多模态数据湖 | 多源异构数据统一获取/存储/处理/调用，元数据管理与数据溯源 |
| L3 五大智能体 + NATS 总线 | 智能体管理中心（智能体集群/交互通信模块/记忆模块/组织模块） | 语义消息协议↔通信协议库；共享状态↔记忆模块；指挥链拓扑↔组织模块 |
| L4 服务层（工作流引擎等） | 工具与应用中心 | 标准化工具接入、工具组合编排与工作流引擎、MCP 化接口 |
| L5 应用层 | 用户交互中心 | 意图解构引擎、认知镜像（可视化决策路径）、动态增强回路 |
| 基座层 LLM 认知中枢 | 大语言模型（LLM）子系统 | 自然语言理解、任务分解、知识融合、协作调度、异常处理、持续优化（论文表1 六大功能维度） |
| 四预闭环 | 四维赋能路径 | 预报↔数据分析与风险识别；预警↔风险预警推送；预演↔风险态势推演；预案/数据接入↔应急数据管理 |

**开题/论文表述建议**：以论文"能力匹配—场景驱动—赋能路径"逻辑组织本课题论证；本课题超出论文的三个增量点（柔性可视化工作流动态重编排、弱网边缘自治协同、五灾种统一建模）作为创新点与专利/论文核心命题。

### 2.3 团队分工与智能体接入边界（v2.1 定案）

两人两线：**平台方**（NexusMind 改造，本方案范围）与**智能体方**（五大智能体的业务智能）。边界规则：**智能体是消息总线上独立的服务，只通过契约交互——不共享代码、不直连数据库、不感知平台内部实现**。这是双方并行开发、互不阻塞的前提。

| 责任域 | 平台方 | 智能体方 |
|---|---|---|
| L1 接入网关/连接器、L2 数据层、L4 服务层、L5 Web、基座（部署/可观测/安全） | ✅ | |
| L3 五大智能体（感知/研判/决策/执行/反馈的智能逻辑） | | ✅ |
| AgentMessage 契约、STU Schema、Subject 规范 | ✅ 定义并冻结 | 遵循 |
| 能力注册中心、共享状态存储、链路追踪 | ✅ | 使用 |
| 埋点量测、回放评测框架、指标报告 | ✅ | 被测对象 |
| Mock 智能体与一致性测试套件 | ✅ | 必须通过 |
| NexusMind 认知资产（`agent_brain.py`/`report_agent.py`/`world_state.py`/`causal_graph.py`） | 移交 | ✅ 作参考起点 |

架构师判断：**契约冻结是全项目第一个关键里程碑**。双方在 M1 内共同评审并冻结《智能体接入规范》v1.0（内容见 §4.3），此后两线并行；契约变更走版本化流程（语义化版本 + 双方签字），禁止口头约定。

## 三、技术选型定案

在架构设计文件给出的候选中定案如下（原则：**贴合其选型方向、控制工程复杂度、最大化 NexusMind 复用**）：

| 层/组件 | 定案 | 取舍理由 |
|---|---|---|
| 后端框架 | **FastAPI**（单体起步 → 按期模块化 → 三期拆微服务） | 架构文件候选 Spring Cloud/FastAPI；Python 生态保留 NexusMind 服务层代码复用；Flask→FastAPI 迁移成本可控（Blueprint→Router），且获得异步、Pydantic 校验（AgentMessage/STU Schema 直接用）、OpenAPI 文档 |
| 前端 | **Vue3 + Ant Design Vue + Cesium（一张图/三维地形）+ Vue Flow（编排画布）+ ECharts** | 架构文件候选 Vue3+ECharts/Cesium/AntD；画布组件补充 Vue Flow |
| 消息总线 | **NATS JetStream** | 架构文件明确 NATS（弱网友好、轻量、发布订阅+请求响应）；JetStream 提供持久化、至少一次投递、消费回放，同时服务 Agent 通信与工作流调度队列 |
| IoT 接入网关 | **EMQX**（MQTT 5.0 为主，CoAP/HTTP 经其桥接；GB/T 28181 视频接入做协议适配器） | 覆盖统一数据接入网关的异构协议要求 |
| 工作流引擎 | **自研 DAG + 状态机轻量引擎**（Temporal/Camunda 作为论文对照调研，不引入运行时依赖） | 架构文件允许自研；自研是专利"柔性动态重编排方法"的载体 |
| 时序库 | **TimescaleDB**（候选 TDengine/TimescaleDB 二选一） | 与 PostgreSQL 同栈，降低运维面；毫秒级写入满足考核 |
| 业务/关系库 | **PostgreSQL 16（+PostGIS 矢量时空）** | 工作流定义库、案例库、预警规则库、STU 存储；PostGIS 支撑风险网格 |
| 知识图谱 | **Neo4j 5**（保留，Graphiti 复用） | NexusMind 现有资产直接复用 |
| 对象存储 | **MinIO** | 影像/视频/雷达原始数据 |
| 缓存 | **Redis 7** | 高频读取、会话、限流（与 NATS 职责分离：Redis 管缓存态，NATS 管消息流） |
| AI 推理 | 统一 OpenAI 兼容接口（复用 `llm_client.py`）+ 边缘小模型路由；PyTorch（GNN POC） | 沿用论文 QLoRA 轻量化路线叙事；TensorRT/Triton 列为三期优化项 |
| 部署 | 开发期 docker-compose → **三期 K8s + Helm**；边缘节点先轻量 Docker、KubeEdge 列为可选试点 | 架构文件三级部署要求；避免一期即背 K8s 复杂度 |
| 可观测 | **Prometheus + Grafana + Loki + Jaeger** | AgentMessage 内置链路追踪 ID，直接对接 Jaeger |

## 四、四大子系统详细设计（对齐架构文件 §4）

### 4.1 高原典型灾种防控任务智能解析子系统（指标1）

**处理链**（照架构文件）：`原始事件 → NLP抽取(LLM) → 灾种分类 → 触发条件识别 → 任务模板匹配 → 标准化任务单元(STU)`

**1. 五灾种领域本体与触发条件规则库**（新建，存 Neo4j 灾情知识图谱）

| 灾种 | 触发条件（规则层示例） | 孕灾因子（监测层） |
|---|---|---|
| 滑坡 | 有效降雨量超阈 + 位移速率加速 + 地下水位抬升 | 降雨、GNSS 位移、InSAR 形变、坡度、岩性 |
| 崩塌危岩 | 冻融循环次数 + 裂缝扩展速率 + 强震/爆破扰动 | 裂缝计、加速度计、温度循环 |
| 泥石流 | 10min 雨强超阈 + 物源储量 + 沟道堵塞度 | 雨量站、物源编目、次声/泥位计 |
| 冰雪雪崩 | 新雪累计 + 风吹雪输运 + 气温骤升 + 雪层弱层发育 | 雪深、雪温剖面、风速 |
| 冰湖溃决 | 冰湖水位快速上升 + 冰舌崩解前兆 + 坝体渗浑水 | 水位、遥感影像时序、坝体形变 |

构建方式：**专家规则库打底 + LLM 辅助扩充 + 人工审核入库**（规则可解释、LLM 覆盖长尾）——此混合模式即论文"语义交互"路径的落地，也是论文写作素材。

**2. 触发条件识别（感知智能体+研判智能体分担）**
- 规则层（快路径）：阈值判断 + 时序特征越限检测（由 NexusMind `world_state.py` 的突变检测/事件检测逻辑改造）；
- 语义层（慢路径）：巡查报告/影像描述/气象文本经 GraphRAG（`vector_store.py` + Graphiti 图检索直接复用）召回灾种知识，判定复合触发条件与灾害链前兆；
- POC 项：GNN 空间风险建模（调研报告建议，借鉴 CC-GRMAS）——一期末用 NASA 全球滑坡目录 + GPM 降水做小规模验证，成功则并入研判智能体，失败则记录负结果入库。

**3. 任务模板匹配与 STU 生成**（新增 `task_decomposer.py`，挂 L4 智能解析服务）
- 任务模板库从本体"防控措施"节点实例化，LLM 按模板做 CoT 拆解；
- STU 采用架构文件规定的 JSON Schema：`任务ID/类型/区域/优先级/责任人/时限/前置依赖`，另增 `required_capabilities/input_data_refs/outputs/fallback_policy` 以衔接工作流调度（STU ↔ 工作流节点一一映射）。

**指标1 量测**：5 灾种历史案例测试集（每类 ≥10 例，含正/负/灾害链例）回放识别，产出逐灾种混淆矩阵与准确率报告；任务拆解以"可编排执行率"衡量。

### 4.2 柔性可视化工作流引擎子系统（指标2，全新自研核心）

**节点类型 ≥10 类**（对齐架构文件清单）：触发、判断、并行、会签、人工、API、消息、设备控制、延时、异常，另增 2 类：数据接入、预警生成——共 12 类，每类节点参数均可在画布侧边栏自定义配置。

**引擎设计**（新增 `backend/app/services/workflow/`）：
- **DAG + 状态机**：`Workflow(带版本) / WorkflowInstance / NodeInstance / Edge` 存 PostgreSQL（JSON Schema 定义配置）；节点类型注册机制，每类实现 `execute(ctx)` / `validate(config)`；
- **动态编排（"柔性"核心，专利点）**：运行中替换节点参数、插入节点、旁路节点；模板与实例版本分离，灾中修订模板不影响在途实例；
- **异常调度**：节点超时/失败/阻塞 → 自动重试 / 任务转移 / 升级上报三段策略；数据源断连触发等待-重试-降级；上游风险等级突变触发运行中改图。异常识别用 JetStream 消费超时监控，快速路径（规则，<1s）+ 复杂改图（LLM 异步）双轨；
- **调度器**：NATS JetStream 作为 ready 队列，事件驱动，节点完成即触发下游拓扑排序调度；工作进程池复用 NexusMind `run_parallel_simulation.py` 的子进程管理骨架。

**可视化画布**（新增 `frontend/src/views/WorkflowDesigner.vue`，Vue Flow）：
- 拖拽建节点/连线、参数配置、DAG 校验（环检测/必填/SLA）；语义上采用 **BPMN 2.0 扩展子集**（网关/任务/事件语义，不实现全 BPMN 规范，论文表述为"BPMN 2.0 扩展"）；
- 预置 5+ 灾种模板（"泥石流蓝色预警流程""冰湖溃决应急会商流程"等）；
- 运行视图实时渲染节点状态（就绪/执行中/成功/失败/降级/重试），复用 NexusMind SSE 事件流机制。

**指标2 量测**：①节点类型清单+配置演示录屏；②"节点就绪→开始执行"埋点差 P95 ≤2s（节点数梯度压测曲线）；③三类异常注入（杀节点/断数据源/风险突变）计时"异常发生→重调度完成" ≤10s。

### 4.3 多智能体协同子系统（平台侧交付：协同框架与智能体接入规范）

平台**不实现智能体**，实现**让智能体协同起来的框架**。本子系统的首要交付物是《智能体接入规范》（Agent Integration Spec），置于仓库 `contracts/` 目录，与智能体方共同评审后冻结、按语义化版本演进。

**1. AgentMessage v1 契约**（Pydantic 定义 + 导出 JSON Schema 发布）
- 字段照架构文件：`msg_id / trace_id / ts / source / target / action / payload / reply_to / in_reply_to`；载荷内嵌结构化断言与引用（对应论文"语义交互"）；
- 总线网关侧强制 Schema 校验：不合规消息拒收并回错误回执——用机制而非约定保证两方实现不漂移。

**2. Subject 规范与消息语义**
- `agent.<类型>.in`（平台→智能体的任务下发）/ `agent.<类型>.out`（智能体→平台的结论上行）、`workflow.<instance_id>.<event>`、`data.<source>.<type>`（数据流订阅）；
- 请求-响应用 JetStream request-reply + 平台侧超时与重试语义；"一次任务委托→确认→执行完成"的事务边界在此定义（协同成功率的度量点）；
- 幂等性约定：`msg_id` 去重，重复投递不产生副作用。

**3. 能力注册中心**：智能体启动时注册能力（灾种域 × 动作）并发心跳；平台按能力路由任务；心跳丢失触发降级（转规则引擎/人工通道）。注册与路由日志同时是协同成功率、同步时延的数据源。

**4. 数据访问边界**：智能体不直连数据库。平台提供两类访问接口——数据查询 API（FastAPI：时序查询/图谱检索/案例检索，即论文"工具与应用中心"的落地）与 `data.*` 流订阅；跨智能体共享状态走带 TTL 的平台侧状态存储 + 变更广播。

**5. 智能体运行支撑（可选脚手架）**：基于 NexusMind `simulation_runner.py` 进程管理骨架提供参考运行器与 Docker 模板，智能体方可选用也可自建（只要遵守契约）。

**6. Mock 智能体与一致性测试门禁**：平台交付五个极简规则版 Mock 智能体（含泥石流场景演示脚本），用途：①平台侧独立开发与联调（不等智能体方进度）；②端到端演示与压测的基线载荷；③一致性验收套件——真实智能体必须通过全部一致性测试（Schema 合法性/超时语义/幂等/错误回执/心跳）方可接入总线，作为两方联调的 CI 门禁。

**指标3 量测**：事务埋点在总线网关、同步时延取 JetStream 消费延迟——量测框架全部在平台侧，与智能体实现质量解耦，且可按智能体归因（报告既能证明平台达标，也为智能体方提供性能反馈）。

**冲突仲裁与组织拓扑**（平台侧框架能力）：优先级 + 抢占式调度 + 投票机制（多研判智能体结论冲突时的仲裁接口）；中心协调式（决策智能体为编排中心）+ 分域自治混合拓扑。弱网收敛以"消息序号+ACK+重传队列"实现（与架构文件 §6.2 一致），CRDT 作为方案表述层。

### 4.3a 五大智能体（智能体方范围，列此仅为契约完整性）

| 智能体 | 契约内动作（示例） | 平台为其提供的接口 |
|---|---|---|
| 感知智能体 | `perceive.anomaly`（弱信号标注上报） | `data.*` 流订阅、时序查询 API |
| 研判智能体 | `assess.hazard`（灾种识别+定级结论） | GraphRAG 图谱检索、案例检索 API |
| 决策智能体 | `plan.stu`（STU 拆解建议）、`plan.reschedule` | STU Schema、工作流模板库、预案检索 |
| 执行智能体 | `execute.notify`（发布指令确认） | 预警发布通道适配器 |
| 反馈智能体 | `feedback.status`（响应/回执分析） | 回执数据流、评估数据 API |

NexusMind 认知资产按上表移交智能体方作参考起点（`world_state.py`→感知、`report_agent.py`+`causal_graph.py`→研判、`evaluation.py`→反馈）。

### 4.4 山地灾害多智能体协同调控平台（指标4）

**1. 多源接入（≤5min）**：新增 `connectors/` 适配器体系（pull HTTP / push MQTT / batch file / 视频 GB28181 适配）：气象 API、雨量/GNSS/裂缝/泥位/雪深/水位监测站、Sentinel-1 InSAR 与光学遥感批处理、人工上报（表单+文本走 LLM 结构化，复用 `text_processor.py`）、Tavily 灾害舆情。网关统一做坐标归一（CGCS2000/WGS84）、时空对齐、异常值剔除。接入时延以"源时间戳→入库可查时间戳"度量，各连接器埋点上报。

**2. 预警生成与靶向触达（≤3min / ≤20min）**
- 生成：研判结论 → 预警生成服务按受众画像（民众/专业救援队/决策领导）生成分级差异化内容，**藏汉双语**（调研报告本地化建议，亦是西藏期刊论文素材）；生成链路全埋点；
- 触达：多通道适配器——短信/北斗短报文（弱网兜底）/应急广播/微信公众号消息推送，按地理围栏（风险网格×行政区划）筛选名单；发布队列本地持久化 + 指数退避重发 + 多通道并发择优；触达回执采集闭环。

**3. 一张图（态势大屏）**：Cesium 三维地形 + 监测站点 + 风险网格着色 + 灾害链推演可视化 + 活跃工作流状态；复用 NexusMind d3 图谱组件做知识图谱/因果链面板。

**4. 三级部署与弱网保障（照架构文件 §6）**
- 一级拉萨/日喀则中心（主+备）：全量数据、知识图谱、模型训练、大屏；
- 二级地市/区县边缘节点：区域汇聚、本地智能体（轻量 Agent + 规则引擎 + 小模型路由）、离线工作流、边缘缓存；
- 三级现场感知/执行节点：监测站、视频前端、应急广播、群防群治终端；
- 弱网四保障：断网自治（边缝始终可独立完成"阈值告警→本地广播"闭环）、消息压缩、可靠重传、链路切换（光纤/4G-5G 主用，北斗/卫星备用）。

**指标4 量测**：接入时延、生成时间、触达时间、预警准确率（新建 `benchmark/`，借鉴 NexusMind 评分框架经验，指标换成触发命中率/预警提前量/区域命中 IoU/等级准确率，回放 5 灾种历史事件全流程）；平台可用性 ≥99.5% 以 Prometheus 统计月度可用度。

## 七、实施路线（双线并行，v2.1）

架构文件四期路线图（M0–M24）不变，工程上按平台/智能体双线组织。**契约冻结（M1 内）是解耦两人进度的关键节点**——此后两线并行互不阻塞。

| 阶段 | 平台方主线（NexusMind 改造） | 智能体方并行线 | 出口标准 |
|---|---|---|---|
| **M1 骨架 + 契约 + 端到端竖切**（最优先） | 删舆情模块；Flask→FastAPI（仅竖切所需 API 域）；NATS/PostgreSQL/TimescaleDB/Neo4j/MinIO/EMQX 容器编排；**AgentMessage 契约 + STU Schema + Subject 规范评审冻结（contracts/ 目录）**；五个 Mock 智能体 + 一致性测试套件；泥石流数据链（气象 API + 模拟雨量站 MQTT）；简版态势页与预警发布页（纯 Web）；全链路埋点 | 参与契约评审；接收 NexusMind 认知资产移交；搭建自有开发沙箱（docker-compose + 平台数据回放流） | 契约 v1.0 冻结；Mock 智能体端到端演示（雨量越限→预警触达）；指标4 时延类首轮实测（≤5min/≤3min/≤20min） |
| **M2 工作流引擎** | DAG+状态机引擎、12 类节点、Vue Flow 画布、动态编排与异常重调度、压测 | 按冻结契约开发五大智能体（沙箱内以 Mock 平台行为联调） | 指标2 量测通过（≥10 类节点/≤2s/≤10s） |
| **M3 智能体接入联调** | 协同框架完善（能力路由/冲突仲裁/降级）；一致性测试门禁上线；真实智能体逐个替换 Mock | 五智能体过门禁接入 | 指标3 量测通过（≤3s/≥90%）；专利1 交底（柔性动态重编排） |
| **M4 扩展与验收** | 5 灾种数据链与本体入库、Cesium 一张图、藏汉双语、边缘节点与弱网演练、K8s 迁移、历史事件回放演练、可用性统计 | 5 灾种识别能力补齐 | 全指标复测达标；指标1 准确率报告；专利2 交底；软著/论文/研究报告齐备 |

架构师说明：为何 M1 即做端到端竖切而非先做工作流引擎——①指标4 的三项时延指标全部落在"接入→感知→研判→预警→反馈"链上，越早拿到基线数据越早暴露瓶颈；②竖切用 Mock 智能体即可完成，不依赖智能体方进度；③工作流引擎（M2）做出来后，竖切链路直接改造成其首个工作流模板，无返工。

## 八、关键风险与对策

| 风险 | 对策 |
|---|---|
| 真实监测数据不可得 | 三级数据策略：①公开数据（气象 API/地震速报/水文公开站）；②历史案例数据集（文献与公报还原）；③符合字段规范的模拟数据发生器——延迟类指标可用仿真数据压测，准确率类指标必须用真实历史案例（口径写入中期报告） |
| Flask→FastAPI 迁移引入回归 | 逐 API 域迁移+每域回归测试；`services/` 层不动，只动接口层 |
| 工作流引擎自研工作量失控 | 严格限定 DAG+状态机+固定节点注册，不做通用 BPMN；画布用 Vue Flow |
| 弱网/边缘指标无法实测 | 一期先用"本地断网演练"（拔网线式混沌测试）度量边缘自治闭环；真实卫星链路指标列为验收前现场测试项，方案口径提前与导师确认 |
| LLM 时延挤占 ≤2s/≤3min 预算 | 指标度量点设计在"调度响应"与"研判结论→预警产物"上；LLM 调用设 SLA 预算与超时降级路径（走规则引擎） |
| 验收口径争议（协同成功率等） | 开题/中期报告中书面定义每个指标量测口径，验收前确认 |
| 西藏本地期刊/学生培养等非技术指标 | 二期启动论文1 投稿（藏汉双语预警/本地化适配为切入点）；联合培养提前安排 |
