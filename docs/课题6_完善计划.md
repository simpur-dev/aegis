## 一、现状结论（一句话）

平台侧四块主体缺口（语义交互、任务智能解析的"智能"部分、真实触达通道、人工上报）**已在 2026-10-03 补齐并实测**：
语义交互服务 + 助手页 + 人工上报端点走的是同一条链路、同一个量测出口；解析升级为规则/检索佐证/LLM 三路融合
（阈值仍是唯一判据），预警规则库版本化 + 标定闭环 + 33 例解析评测集都能复跑取证；触达通道从
`NotImplementedError` 变成带主机白名单闸与回执的真实 HTTP 适配器。**剩下的缺口分两类**：
数据与凭据（现场标注案例集、真实网关凭据、真 DEM/影像、LLM 对照跑、部署形态合账）与
成果申报（批次 E）——这两类都不是"再写代码"能关掉的。多智能体本体仍由外部团队交付，
接入位与门禁早已就位（`agents/`），真样本等对方过门禁后由平台网关量测。

- **唯一新增的排期风险**：指标 3 的协同成功率/同步时延**真样本**依赖外部交付时间。缓解：量测点全在平台网关（规范 §8，与智能体实现解耦）、门禁全自动、mock 全链路可演示——对方一到，接入成本是一次联调而不是一段开发。
- 硬依赖只有两样：**LLM API key**（B/C 的智能路径需要；无 key 全部可降级开发，但实测数字要有 key 才算数）、**D4 需要 compose 整栈**（依赖与网络拓扑坑已清，见 REPORT）。
- v1.4 复核追加**第三类依赖：需要现场/项目方决定的口径**，不是写代码能关掉的——① 数据分级的前置（谁调平台 API、带什么凭据、哪些字段算敏感；REPORT 第 17 项）；② 链路切换（光纤/4G-5G/北斗短报文）要的是可切的目标出口与空口条件（REPORT 第 16 项）；③ 真实触达网关的地址与回执格式（第 3 项）；④ 现场标注案例集（第 9 项）。这四项各缺一件外部输入，缺哪件就如实挂着哪件。
- 每批合并前门禁不放松：`ruff format --check` + `ruff check` + `mypy` + 全量 `pytest` 全绿；新增可选能力一律走 `integrations.py` 唯一装配点，"装配时跳过"与"跑起来后降级"两行事实分开。
